IMPORTANT CAVEAT

Replay is not time travel.

What it does: reuse recorded results for the longest unchanged prefix of completed agent() calls in the same session.

What it does not do: guarantee deterministic inference, fresh repository state, or exactly-once filesystem and external side effects.

Operational rule: mutating agents still need idempotent instructions, state inspection before writes, managed isolation, and verification afterward.

04 / DESIGN OPTIONS

Five ways to make agents programmable.

They are not mutually exclusive. The critical decision is which layer becomes the source of truth.

A / BOOTSTRAP

Model-generated Bash

Let the model compose devspace agents run/show commands and use ordinary process tools.

GOOD

  • ✓ Already works
  • ✓ Human-debuggable commands
  • ✓ No new protocol required
  • ✓ Flexible for experimentation

LIMIT

  • × Fragile text parsing and quoting
  • × Opaque intent to host policy/UI
  • × No typed events or cancellation
  • × Encourages polling and shell glue
  • × Broad shell capability exceeds agent task need

B / MODEL API

First-class MCP tools

Give models narrow, typed operations such as start_agent, read_agent_events, and cancel_agent.

GOOD

  • ✓ Typed validation
  • ✓ Fine-grained approval
  • ✓ Native UI rendering
  • ✓ Auditable model intent
  • ✓ No shell parsing

LIMIT

  • × Tools alone do not create a scheduler
  • × Model context can fill with polling/events
  • × Requires a durable service underneath

C / INTERNAL API

Direct TypeScript service

Expose a reusable application service to the CLI, MCP server, UI, and tests.

GOOD

  • ✓ One source of lifecycle truth
  • ✓ Strong typing and testability
  • ✓ Natural access to adapters and DB
  • ✓ Surfaces can remain thin

LIMIT

  • × Not directly programmable by a model
  • × API design must account for streaming and restart recovery

D / WORKFLOW LANGUAGE

Restricted JavaScript runtime

Let the model author workflow scripts with injected primitives modeled after agent(), pipeline(), and parallel().

GOOD

  • ✓ Deterministic control flow
  • ✓ Expressive loops and aggregation
  • ✓ Compact orchestration context
  • ✓ Reusable workflows

LIMIT

  • × Largest security/runtime surface
  • × Replay semantics are subtle
  • × Premature without events, cancellation, and scheduler
  • × VM restriction is not OS sandboxing

E / RECOMMENDED

One service, many surfaces

Build lifecycle, events, policy, and scheduling once. Wrap it with MCP and CLI now; add the workflow runtime after the foundation is trustworthy.

NOW

  • 1. Durable orchestration service
  • 2. Handle-based provider adapters
  • 3. Typed MCP agent tools
  • 4. CLI delegates to the same service

LATER

  • 5. Scheduler and worktrees
  • 6. Structured artifacts
  • 7. Restricted workflow runtime
  • 8. Journaled replay where valuable
Verdict on the Bash hypothesis

Your bias is useful for bootstrapping. A capable model can absolutely author the CLI commands. But shell should remain a compatibility and human-operations surface—not the canonical protocol—because DevSpace cannot reliably inspect, authorize, stream, cancel, recover, or visualize orchestration hidden inside arbitrary Bash.

07 / SAFETY MODEL

Isolation is not permission.

Capability policy

Define provider-neutral modes—read-only, workspace-write, full access, network, secrets—and translate them per adapter. Fail closed when a provider cannot enforce the requested policy.

Worktree isolation

Use separate Git worktrees for concurrent writers to avoid collisions and simplify review. This protects repository state, not the host OS or credentials.

Environment policy

Do not pass the entire parent environment by default. Construct an allowlisted environment and explicitly broker secrets only when a run policy allows them.

Prompt boundaries

Treat source files, web pages, tool output, and prior-agent text as untrusted data. Label provenance and avoid interpolating untrusted results into privileged instructions.

CURRENT SECURITY DEBT TO FIX BEFORE BROAD ORCHESTRATION

Claude runs with bypassed permission checks and currently ignores the requested write mode.

Cursor/Copilot ACP permission requests are automatically accepted rather than adjudicated by a DevSpace policy.

Read-only intent in profiles is prompt-level guidance, while detached workers inherit a broad host environment.

08 / BUILD ORDER

Earn the workflow runtime.

Do not begin by cloning pipeline(). First make a single agent run observable, controllable, recoverable, and policy-bound.

4

5

09 / COPY SELECTIVELY

Take the pattern. Not every implementation detail.

Copy

  • ✓ Code-owned control flow
  • ✓ Fresh context per worker
  • ✓ Schema-validated handoffs
  • ✓ Bounded concurrency
  • ✓ Explicit phases and labels
  • ✓ Worktree option for writers
  • ✓ Budget-aware loops

Reconsider

  • △ Same-session-only replay as the only recovery model
  • △ In-process VM as a strong security boundary
  • △ Prefix replay for side-effect-heavy workflows
  • △ Provider-specific permission escape hatches
  • △ Unstructured text as the default task artifact
  • △ Building workflow syntax before lifecycle correctness

FINAL POSITION

DevSpace should become the harness.

Let the model decide the work graph: which configured profile to use, what prompt to send, which tasks can run concurrently, how to verify results, and when to stop.

Let DevSpace own execution mechanics: IDs, policy, scheduling, event capture, cancellation, provider translation, isolation, recovery, and durable state.

Keep CLI available: excellent for humans, debugging, scripts, and compatibility. Route it through the same service rather than letting it become a second runtime.

Add dynamic workflows last: once startAgent() is trustworthy, wrapping it in agent(), pipeline(), and parallel() becomes a tractable language-design problem.

DECISION: HYBRID, SERVICE-FIRST CLI → MCP → SCHEDULER → WORKFLOW VM
